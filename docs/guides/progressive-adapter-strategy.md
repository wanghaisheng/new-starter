# 渐进式适配器策略（Progressive Adapter Strategy）

本项目采用渐进式适配器策略，实现从本地开发到大规模生产环境的平滑演进，支持配置、服务、数据存储等多层的弹性升级与切换。

---

## 1. 核心里念
- **适配器模式**+**工厂模式**，实现底层实现与业务解耦。
- **配置驱动**，通过环境变量/配置文件动态切换 adapter，无需改动业务代码。
- **渐进式升级**，支持从 Mock、本地存储到远程/集中式服务的平滑迁移。

---

## 2. 典型应用场景

### 配置中心（ConfigService）
- 阶段一：仅用本地环境变量/文件（EnvConfigAdapter）。
- 阶段二：增加本地缓存（如 LocalStorage/IndexedDB）。
- 阶段三：接入远程配置中心（如 Apollo、Consul、Firebase Remote Config），并组合本地缓存，支持热更新、灰度、容灾。

### 数据服务（DataService）
- 阶段一：本地 Mock/IndexedDB/SQLite，适合开发和离线场景。
- 阶段二：本地+远程同步，支持断网容灾、冲突解决。
- 阶段三：远程数据库/集中式服务为主，支持弹性扩容和多端一致性。

### 业务服务（Service Layer）
- 阶段一：MockService，快速开发调试。
- 阶段二：本地/轻量服务。
- 阶段三：远程/云服务，支持灰度、弹性伸缩。

---

## 3. 切换与升级机制
- 通过环境变量（如 CONFIG_ADAPTER、DB_ADAPTER、SERVICE_ADAPTER）或配置文件切换 adapter。
- 工厂/注册中心根据配置动态组合/注入合适的实现。
- 支持平滑升级、灰度发布、回滚。

---

## 4. 业务零侵入
- 业务层始终通过统一接口（如 configService、dataService、useXXX）访问，底层切换对业务透明。
- 禁止业务代码直连底层实现。

---

## 5. 推荐实践
- 新增 adapter 时实现统一接口并注册到工厂。
- 变更适配器/环境变量需同步更新相关文档。
- 推荐在 CI 中校验关键配置项与文档一致性。

## 8. 阶段性演进与产品成长路线

渐进式适配器策略可以帮助产品和团队在不同阶段（0-1、1-10、10-100）高效开发、快速响应需求和弹性扩容：

### 阶段一：0-1（初创/探索期）
- **Mock/本地适配器优先**，无需后端依赖，接口快速迭代，前后端并行。
- 统一接口/工厂注入，重构和返工成本极低。
- 自动化测试友好，开发效率高。

### 阶段二：1-10（成长/试运营）
- 平滑切换远程/集中式服务，只需扩展 RemoteAdapter 并调整配置。
- 支持灰度/渐进上线，部分服务先切远程，风险可控。
- 新需求快速响应，主流程代码不变。

### 阶段三：10-100（扩展/规模化）
- 弹性扩容，支持本地缓存+远程同步，读写分离，多实例高并发。
- 多端协同/多环境支持，配置和数据层自动适配。
- 容灾/回滚/性能优化，组合适配器提升弹性和可维护性。

#### 具体收益
- **极大缩短开发周期**，开发初期无需等待后端，接口和业务并行推进。
- **快速响应变化**，新需求/新场景/新技术选型随时接入。
- **弹性扩展**，业务量激增时只需切换/扩展 adapter，无需大规模重构。
- **团队协作高效**，前后端、测试、运维各自解耦。

## 9. 实践建议
- 在项目文档中明确渐进式策略和切换方法。
- 统一所有服务、数据、配置访问接口，禁止业务层直连底层实现。
- 每次扩展/切换 adapter 时补充工厂注册和文档说明。
- 在 CI/CD 流程中校验 adapter 注册和接口一致性。

## 10. 配置驱动与 Feature Flag

- 所有环境参数、策略、特性开关均通过 ConfigService 统一管理，禁止硬编码。
- 支持多环境（dev/test/prod）、多租户、灰度、A/B 实验和动态开关等场景，业务层代码零侵入。
- 推荐采用 FEATURE_FLAGS 配置对象，按需动态控制新功能上线、A/B 实验、紧急开关等。
- 配置变更需同步更新配置文档，支持类型校验和变更审计。
- 典型结构示例：

```json
{
  "API_BASE_URL": "...",
  "ENV_STAGE": "prod",
  "FEATURE_FLAGS": {
    "newUI": true,
    "betaQuiz": false,
    "enableAds": true,
    "experimentX": "groupA"
  },
  "BRAND": "heytcm"
}
```

- 业务代码用法示例：

```typescript
const featureFlags = configService.get('FEATURE_FLAGS');
if (featureFlags?.newUI) {
  // 渲染新版UI
}
if (featureFlags?.betaQuiz) {
  // 显示实验性Quiz功能
}
```

- 推荐将 Feature Flag 体系与 CI/CD、发布流程集成，支持一键开关、回滚和类型校验。

## 11. 监控、日志与可观测性

- 已有统一日志服务，建议所有关键业务流程、异常、告警均通过日志服务采集，日志分级与结构化便于后续分析。

### 分阶段演进建议

#### 阶段一：日志优先（0-1）
- 日志服务全量覆盖主流程、异常、告警，便于开发调试和初步问题定位。
- 日志分级（info/warn/error/debug）与结构化，便于后续分析和检索。
- 日志采集通过适配器/工厂模式实现，支持本地/云端/第三方方案切换。

#### 阶段二：基础监控（1-10）
- 引入系统级监控（如接口可用性、响应时间、错误率、资源占用等），可用 Prometheus、Grafana、云监控等工具。
- 关键指标自动告警，支持邮件/IM/短信等通知。
- 监控配置通过 ConfigService 统一管理和动态调整。

#### 阶段三：埋点与可观测性（10-100）
- 埋点采集用户行为、业务事件、转化漏斗，支持 A/B 实验与数据驱动决策。
- 引入分布式追踪（如 OpenTelemetry、Jaeger），支持链路追踪、性能瓶颈定位。
- 日志、监控、埋点、追踪数据打通，支持端到端分析和全链路可观测。
- 埋点与业务解耦，推荐统一 trackEvent/monitor/report 接口，便于后续批量接入第三方分析平台。

### 最佳实践
- 日志、监控、埋点均建议采用适配器/工厂模式，便于平滑切换和扩展，配置通过 ConfigService 管理。
- 所有埋点/监控/日志变更需同步更新文档和数据字典，保证数据一致性和可用性。

## 12. 统一异常处理与用户提示

### 统一异常处理工具/组件的渐进式演进

#### 阶段一：基础异常提示（0-1）
- 页面/组件通过 hooks 返回的 error 字段手动渲染错误提示。
- 提供简单的 Loading/Error/Empty 组件，快速覆盖主流程异常。

#### 阶段二：全局异常处理与提示（1-10）
- 引入全局 Toast/Snackbar/Modal 组件，所有 hooks 内部异常处理时自动调用 triggerToast/setToastMessage，用户可在任意页面获得一致的错误提示。
- 实现 ErrorBoundary 组件捕获未处理异常，防止页面崩溃。
- 提供统一的异常提示样式和文案规范。

#### 阶段三：多样化与可扩展异常提示（10-100）
- Toast/Snackbar/Modal 支持多类型（success/error/warning/info），并可配置多语言、个性化提示。
- 异常提示与埋点/日志/监控体系打通，异常发生时自动上报分析。
- 支持自定义异常处理策略（如自动重试、降级、兜底页面等）。

### 最佳实践
- 所有异常提示均通过统一工具/组件（如 triggerToast、ErrorBoundary、Modal）实现，页面和业务层无需重复造轮子。
- 提示组件风格、交互和文案统一，便于后续扩展和国际化。
- hooks/README.md 和异常处理最佳实践文档需同步更新。

## 13. 预留扩容和弹性设计

### 分阶段演进建议

#### 阶段一：基础弹性（0-1）
- 采用工厂/注册中心模式（如 ServiceRegistry/AdapterFactory），所有服务和适配器通过统一注册中心获取，便于后续扩容和切换。
- 支持本地优先存储（如 IndexedDB/SQLite），满足开发和小规模测试的离线、容灾需求。

#### 阶段二：弹性组合与同步（1-10）
- 实现本地优先+远程同步组合方案，数据可在本地离线缓存，也可与远程服务同步，支持灰度切换和弹性扩容。
- 适配器和同步管理器（如 SyncManager）支持多端数据一致性和冲突解决。

#### 阶段三：大规模弹性与分布式（10-100）
- 架构预留分布式、集群、云原生等能力，支持高并发、横向扩容和多活部署。
- 服务注册中心和适配器体系支持动态发现和弹性调度。
- 业务层零侵入，扩容和切换无需大规模重构。

### 已落地能力
- 已实现工厂/注册中心模式，所有服务和适配器均通过统一注册中心获取，便于横向扩容和弹性切换。
- 已支持本地优先+远程同步组合，满足离线容灾和高并发扩展需求。
- 项目架构已预留进一步弹性扩展的能力。

## 14. 领域分层与解耦 & 领域驱动 hooks + 统一状态/服务注册中心

### 已实现能力

#### 领域分层与解耦
- 项目已严格分层：UI 组件层、业务 hooks 层、服务层（Service）、适配器层（Adapter）、数据/配置层等，各层职责清晰、解耦良好。
- 业务逻辑、数据访问、配置管理等均通过接口和抽象解耦，便于后续扩展、重构和测试。
- 领域模型、服务协议、适配器接口等均有独立定义，支持 Mock、测试和多实现切换。

#### 领域驱动 hooks + 统一状态/服务注册中心
- 所有页面/组件的数据流全部通过领域驱动 hooks（如 useUser、useMatches、useMessages 等）获取和变更，禁止直接调用 ServiceFactory/Service。
- hooks 返回值统一包含 loading、error、empty 字段，error 字段已细化为分类型，便于页面精准渲染和用户友好提示。
- hooks 内部服务实例全部通过统一的 Registry 获取，禁止 Factory 直连，支持自动降级到 mock service。
- 统一状态与服务注册中心机制已落地，便于服务实例动态注入、mock/real/remote 平滑切换，业务层零侵入。
- hooks/README.md、测试用例和最佳实践文档已同步完善，后续新 hooks 必须遵循此规范。

## 15. 基础 hooks 与业务 hooks 分层实践（以 message 为例）

为提升复用性、开发效率与复杂业务适配能力，建议采用“基础 hooks + 业务 hooks”分层模式，适配产品从 0-1、1-10、10-100 各阶段。

### 分阶段演进建议

#### 阶段一：基础数据 hooks（0-1）
- 以 useMessageList/useMessageEntity 等基础 hooks 为主，封装最小化的数据获取、状态管理（loading/error/empty）和简单操作。
- 适合快速开发、原型和标准数据流场景，模板化生成效率高。

#### 阶段二：组合与扩展（1-10）
- 在基础 hooks 之上，组合和扩展业务 hooks（如 useMessages），实现分页、批量操作、事件监听、复杂错误处理等。
- 支持多 hooks 组合（如 useUser + useMessages），提升业务灵活性。

#### 阶段三：复杂业务与高阶 hooks（10-100）
- 业务 hooks 进一步封装多端同步、实时推送、缓存、乐观更新等高级能力。
- 支持高阶 hooks（如 usePaginatedList、useRealtimeMessages），便于团队协作和大规模扩展。

### 推荐分层模式

- 基础 hooks：只做最小数据获取和状态管理，便于模板化和复用（如 useMessageList、useMessageEntity）。
- 业务 hooks：组合基础 hooks，扩展业务操作和复杂逻辑，页面只依赖业务 hooks（如 useMessages）。
- 目录结构建议：
  ```
  src/core/hooks/
    useMessageList.ts      // 基础 hooks
    useMessageEntity.ts    // 基础 hooks
    useMessages.ts         // 业务 hooks，组合和扩展
  ```

### 实践收益
- 标准化、模板化基础 hooks，提升开发效率和一致性。
- 复杂业务灵活扩展，团队协作与维护无障碍。
- 适配产品不同阶段需求，支持渐进式演进。

## PWA 架构下的渐进式适配器实践

渐进式适配器策略与 PWA（Progressive Web App）架构天然契合，可实现多端一致性、离线能力与渐进增强：

- **全生命周期适配**：
  - 开发阶段可用本地 mock/provider，支持热重载、断网模拟与本地缓存，提升前端开发体验。
  - 测试阶段可动态切换 provider，模拟多端同步、离线恢复、冲突解决。
  - 生产阶段通过远程/混合 provider，结合 Service Worker 实现离线缓存、数据同步、实时推送等能力。

- **核心变量联动**：
  - 结合 `NEXT_PUBLIC_NODE_ENV`、`NEXT_PUBLIC_ENV_STAGE`、`NEXT_PUBLIC_DATA_MODE`、`NEXT_PUBLIC_PLATFORM` 等环境变量，自动切换不同 provider 及运行模式。
  - 配置服务统一管理所有 provider/adapter，保证多端/PWA 下的配置一致性与安全性。

- **PWA 特有能力**：
  - Service Worker 支持静态资源与数据缓存，断网可用，自动同步。
  - IndexedDB/SQLite 等本地存储方案与远程 provider 组合，支持混合/渐进式数据管理。
  - 支持推送、消息实时性、前后台同步、渐进式增强等。

- **最佳实践**：
  - 所有 hooks、服务、适配器均应支持 provider 自动切换与热更新，适配 PWA 场景下的离线、同步、缓存、冲突解决等需求。
  - 强调类型安全、配置服务统一入口、环境变量全链路同步，降低多端维护复杂度。

> 渐进式适配器策略为 PWA 应用的多端适配、离线体验、数据一致性与弹性扩展提供了坚实基础，是现代前端架构的推荐模式。
