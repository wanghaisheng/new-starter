# 旧服务迁移任务文档

## 目标

将核心业务服务（如 match、member、growth、task、profile 等）下的旧实现迁移至 `src/core/services/business/deprecated`，并确保类型安全、分层清晰。补齐依赖的 repository，统一采用类型安全架构。保留兼容性，逐步淘汰旧代码。

---

## 迁移任务拆解

### 阶段一：服务梳理与目录规划

1. **梳理待迁移服务**
   - 列出所有 `src/core/services/business` 下的业务服务目录（除 user 外）。
   - 标记哪些服务有旧实现需迁移。

2. **规划 deprecated 目录结构**
   - 按业务分子目录或统一放置，保持迁移后结构清晰。

### 阶段二：仓储层检查与补齐

3. **检查 repository 是否存在**
   - 对每个服务涉及的实体，检查 `src/core/lib/db/repositories/impl` 下是否有对应 repository。
   - 如缺失，按类型安全架构新建，并集成 EntityConverter。

### 阶段三：服务迁移与适配

4. **迁移服务代码**
   - 将旧服务实现迁移到 `deprecated` 目录，调整导入路径，保证依赖 repository 层。
   - 对所有数据库操作做 repository 封装，禁止直接操作底层 dataService/ORM。

5. **接口适配与兼容性处理**
   - 保留兼容性包装，必要时增加 `@deprecated` 注释。
   - 明确类型声明，保证类型安全。

### 阶段四：文档与维护说明

6. **补充迁移说明文档**
   - 在 `deprecated` 目录下维护 `README.md`，说明迁移目的、维护策略、已迁移服务清单。

### 阶段五：测试与回归

7. **补充/修正测试用例**
   - 针对迁移服务，补充或修正单元测试，确保迁移后功能一致、类型安全。

---

## 迁移最佳实践补充

- 在迁移每个旧服务时，**必须先罗列该服务的全部接口/方法清单**，逐一检查并迁移，确保无遗漏。
- 对于依赖其他服务或有复杂业务逻辑的方法，需明确注入依赖、适配类型安全架构。
- 迁移完成后建议用对照表或测试用例确保新旧服务功能等价。

---

## 任务优先级建议

1. 优先迁移与主业务强相关、变更频繁的服务（如 match、member）。
2. 其次迁移辅助性、低频次服务（如 growth、task、profile）。
3. 最后梳理零散工具类、通用服务等。
