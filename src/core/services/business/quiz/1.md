# Quiz 服务架构与设计 FAQ

---

## 1. Adapter 的定位

- adapter（如 MBTIQuizAdapter、TCMQuizAdapter、BaziQuizAdapter）是“测评类型的核心业务适配器”，主要负责：
  - 聚合数据访问（repository）
  - 实现测评类型的主流程（如特殊评分、专属报告生成、命盘分析等业务主逻辑）
  - 适合实现“类型专属的主流程”，如八字命理的命盘分析、MBTI 的性格类型判断等
- 适配器是“主流程的变体”，通常每种 quiz type 只会有一个 adapter。

---

## 2. Enhancer 的定位

- enhancer 是“增强器”或“插件”，用于在主流程前后“插拔”附加能力，典型场景有：
  - beforeSave：保存测评结果前的自动打标签、内容安全检测、AI 纠错、埋点等
  - afterSave：保存后推送通知、数据同步、AI 报告生成、埋点等
- enhancer 适合实现“横切关注点/通用增强能力”，可为所有类型测评复用/组合。
- enhancer 是“插件式能力”，可以多个叠加、动态配置、随时扩展。

---

## 3. Adapter 与 Enhancer 的区别与协作

- adapter 负责“主流程变体”，类型专属业务逻辑（如命盘分析、MBTI 评分）
- enhancer 负责“横切增强”，通用插件能力（如安全检测、AI 标签、推送等）
- 两者解耦，既保证主流程可扩展，也保证增强能力可插拔、可组合。

---

## 4. 为什么要为不同 quiz type 预留 adapterMap 机制？

- 现在所有 quiz type 用同一个 QuizAdapter 完全合理，adapterMap 只注册 default 即可。
- 未来如有业务差异（如 TCM、八字等类型有特殊评分/报告/数据源），只需实现新 adapter 并注册到 adapterMap，无需重构主流程。
- adapterMap 机制为未来差异化、A/B 测试、插件扩展等场景预留弹性。

### 典型 wiring 示例
```typescript
import { MBTIQuizAdapter } from './adapters/mbti-quiz-adapter';
import { TCMQuizAdapter } from './adapters/tcm-quiz-adapter';
import { BaziQuizAdapter } from './adapters/bazi-quiz-adapter';
import { QuizAdapter } from './adapters/quiz-adapter';

const adapterMap = {
  mbti: new MBTIQuizAdapter(quizRepository),
  tcm: new TCMQuizAdapter(quizRepository),
  bazi: new BaziQuizAdapter(quizRepository),
  default: new QuizAdapter(quizRepository),
};
```

---

## 5. QuizService 架构核心

- 构造函数注入 configService、adapterMap、enhancerMap，实现类型和能力的配置驱动。
- 通过 enhancerMap 支持保存前/后处理（如自动打标签、内容安全、AI报告等），实现插件化能力。
- 业务逻辑全部通过 QuizService 暴露，外部不直接依赖 repository/adapter。

---

## 6. 推荐最佳实践

- adapterMap、enhancerMap 均在 wiring/init 阶段集中注册，便于统一管理和自动化测试。
- 新增 quizType 或增强能力时，仅需实现 adapter/enhancer 并注册到 map，无需重构主流程。
- 所有类型、接口、插件均集中在 types/adapters/enhancers 目录，便于团队协作和维护。

---

## 7. 示例增强器

```typescript
export class DemoEnhancer implements IQuizEnhancer {
  async beforeSave(result: QuizResult): Promise<QuizResult> {
    // 可在此添加保存前的处理逻辑，如自动打标签、内容安全检测等
    return result;
  }
  async afterSave(result: QuizResult): Promise<void> {
    // 可在此添加保存后的处理逻辑，如推送通知、埋点、AI 分析等
    return;
  }
}
```

---

## 8. 典型目录结构建议
- types/  类型定义与接口
- service/  核心业务逻辑
- adapters/  数据/AI/报告等适配器
- enhancers/  增强器插件（如内容安全、AI分析等）
- registry/  服务注册表
- factory/  工厂方法
- __tests__/  单元测试
