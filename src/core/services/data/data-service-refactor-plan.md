# 数据服务解耦与注册表工厂模式改造计划

## 一、改造目标

- 实现数据服务（DataService）全链路解耦：配置服务、工厂、注册表、适配器分层清晰，支撑 Mock/本地/云端/混合多环境无缝切换。
- 统一业务层、仓储层、hooks 的数据访问入口，禁止直接 new，全部通过注册表和工厂获取实例。
- 支持插件化、A/B 测试、Mock 自动降级、环境参数动态注入。
- 提升架构可扩展性、可维护性和测试友好性。

## 二、现状梳理

- 已有多种数据服务适配器（sqlite、indexeddb、mock 等），但部分实例创建方式分散，存在直接 new、硬编码环境判断等问题。
- 工厂（DataServiceFactory）和注册表（DataServiceRegistry）已初步实现，但文档与用法尚未全面统一。
- 配置服务（configService）可读取环境变量，尚需规范与工厂、注册表协作方式。

## 三、改造方案

1. **配置服务集中管理环境与参数**
   - 所有环境变量、运行参数、adapter 选择均通过 configService 获取，禁止硬编码。
   - 工厂和注册表仅依赖配置服务，不再分散判断。
   - 关键环境变量包括：
     - `NEXT_PUBLIC_DATABASE_ENV`（mock/local/dev/prod，决定主运行阶段）
     - `NEXT_PUBLIC_DATA_MODE`（online/offline/hybrid，决定运行模式）
     - `NEXT_PUBLIC_ONLINE_DB`、`NEXT_PUBLIC_OFFLINE_DB`（供应商选择）
   - 推荐所有 key 统一通过 config-keys.ts 管理。
2. **工厂统一实例化数据服务**
   - DataServiceFactory 负责根据配置服务动态选择适配器并实例化。
   - 支持 Mock、本地、云端、混合等多 adapter 动态切换。
   - 工厂内部先判断环境阶段，再判断数据模式，最后根据模式选择具体供应商。
   - 新增/扩展 provider 只需实现对应 adapter 并注册，无需改动工厂主逻辑。
3. **注册表全局唯一获取实例**
   - DataServiceRegistry 负责注册、获取和管理数据服务实例，保证全局唯一、懒加载。
   - 业务层、仓储层、hooks 统一通过注册表获取实例，禁止直接 new。
   - 注册表支持运行时热切换和 Mock 自动降级。
4. **仓储层与数据服务解耦**
   - 所有仓储类通过依赖注入或注册表获取数据服务实例，禁止直接依赖底层数据库 client。
   - 支持 Mock/测试/本地/云端灵活切换，业务层无感知。
   - 仓储层推荐只依赖统一接口（IDataService/IBaseRepository）。
5. **文档与最佳实践同步更新**
   - 补充 data/README.md，明确“配置服务+工厂+注册表+适配器”全链路解耦模式与推荐调用链。
   - 在仓储、服务、hooks 文档中统一强调注册表获取实例原则。
   - 给出关键配置项、选择流程与代码示例，便于团队参考和落地。

## 四、分步实施计划

1. 梳理现有适配器、工厂、注册表实现，补充缺失的配置读取与注入逻辑，确保所有选择均通过 configService 和 config-keys.ts。
2. 规范所有实例创建方式，移除直接 new 和分散环境判断，全部迁移到工厂+注册表，支持多环境/多供应商自动切换。
3. 优化 configService，完善环境变量、运行参数管理与类型定义，确保所有关键 key 集中管理。
4. 升级 data/README.md 与相关文档，补充标准调用链、配置驱动选择机制与设计要点。
5. 编写自动化测试，验证 Mock/本地/云端/混合多环境切换与注册表获取实例的正确性。
6. 推动团队成员统一采用注册表+工厂+适配器模式开发与维护数据服务，定期 code review 检查。

## 五、预期收益

- 环境切换、Mock/测试、插件化等场景零侵入，业务层和仓储层开发体验提升。
- 架构分层清晰，易于扩展新 adapter、支持多端和未来新业务需求。
- 测试友好、Mock 自动降级、A/B 测试等能力提升。
- 团队协作和维护成本大幅降低。

## 六、数据服务自身的核心改造点

本节聚焦于数据服务(DataService)自身的工程细节和鲁棒性，区别于与其他模块整合的全局考量：

1. **初始化状态标志与幂等性**
   - 数据服务应暴露“已初始化”状态，防止业务层/仓储层在未初始化前访问数据。
   - 初始化流程具备幂等性，重复调用不会产生副作用。
2. **adapter/provider 热插拔能力**
   - 支持运行时根据配置热切换 adapter/provider，便于测试和环境切换。
   - 切换时需考虑资源释放与数据一致性。
3. **服务实例生命周期管理**
   - 注册表/工厂支持服务实例的销毁与重建，避免内存泄漏或旧实例残留。
   - 支持“重置数据服务”场景（如用户切换、环境切换时）。
4. **健康检查与异常上报机制**
   - 内置健康检查（如连接状态、schema 检查等），并对异常统一上报，便于业务层/监控系统感知。
5. **与 hooks/仓储层的类型约束与契约**
   - 明确数据服务与仓储层的接口契约，保证类型安全，避免因底层 provider 差异导致的类型不一致。
6. **测试与回归保障**
   - 明确自动化测试覆盖要求，尤其是多环境、多 provider 下的行为一致性。

**第二阶段（鲁棒性与高级能力）**

8. 服务实例生命周期管理（销毁/重建/重置）

- 配置服务、工厂、注册表是整个体系的基础，必须优先梳理。

- 自动化测试和文档应在主要功能实现后同步推进，确保质量和团队协作。
