# hooks 与服务层一致性细节问题分析

## 1. 部分 hooks 服务实例获取方式不完全统一
- 部分 hooks（如 useImageUploadQueue、useSensor、useLocation、useBluetooth 等）直接通过 Factory.create/createService 获取服务实例，而不是统一通过 Registry.getDefaultService。
- 这种情况多见于设备类服务（如蓝牙、相机、定位、传感器等），这些服务架构上采用简单工厂模式，无需注册表，导致服务实例获取方式与业务数据类 hooks（如 useUser、useMatches）存在差异。
- 建议：如有必要，可为设备服务也提供统一的 Registry 入口，保持调用风格一致。

## 2. 部分 hooks 的 error/empty 状态处理不够细致
- 某些 hooks（如 useAiImageTaskQueue）未将 error/empty 状态完整暴露给页面，或者异常处理后未传递给调用方，导致页面无法友好渲染错误或空态提示。
- 建议：所有业务 hooks 返回值应包含 loading、error、empty，并在异常时通过 triggerToast 或 setToastMessage 给予用户反馈。

## 3. 参数签名与类型统一性
- hooks 与服务层的参数签名近期已做过统一，但仍需持续关注后续服务扩展时是否保持一致，避免因签名不一致导致类型报错或 hooks 内部调用异常。

## 4. 设备类服务 hooks 的初始化副作用
- 某些设备 hooks（如 useSensor、useBluetooth、useCamera）在 useEffect 中直接注册所有适配器并初始化实例，副作用较重，可能影响首次渲染性能。
- 建议：可考虑延迟初始化或按需注册，减少无用副作用。

## 5. Mock/Remote 自动降级一致性
- 虽然大部分 hooks 能根据环境变量自动切换 mock/remote，但部分 hooks 对环境变量的处理方式不完全一致，存在直接硬编码 'mock' 或 'remote' 的情况。
- 建议：统一通过环境变量配置服务类型，避免硬编码。

## 6. useNotifications 存在的问题分析
- **empty 状态未暴露**：useNotifications 返回值未包含 empty（空数据）状态，页面无法直接判断通知列表是否为空，影响空态友好渲染。
- **服务实例依赖 useRef，未做类型约束**：serviceRef 类型为 any，建议增加类型约束，提升类型安全。
- **副作用依赖不完整**：useEffect 依赖仅为 userId，未包含 type、apiBaseUrl，若环境变量动态变化时服务实例不会自动更新，可能导致数据不一致。
- **fetchNotifications 方法依赖问题**：fetchNotifications 被 useEffect 间接调用，但未加入依赖数组，理论上可能导致闭包引用旧值（虽然此处实际影响较小）。
- **异常处理一致性**：虽然已通过 triggerToast 反馈异常，但 error 状态未区分不同操作（如 fetch/markAsRead/delete），建议细化错误类型或增加最近操作标识，便于页面精准提示。
- **未实现 Mock/Remote 自动降级兜底**：虽然支持环境变量切换，但若服务创建失败未有兜底 fallback 逻辑。

## 7. useAuth 存在的问题分析
- **返回值未包含 empty 状态**：useAuth 返回的 AuthState 未包含 empty（空数据）标识，页面无法区分“未登录”与“用户数据为空”两种场景。
- **enabledMethods 类型与用途不明**：enabledMethods 仅为空数组，未实际从服务端或 provider 获取，建议完善。
- **副作用依赖不完整**：useEffect 初始化 provider 时仅依赖 triggerToast，未包含环境变量（如 NEXT_PUBLIC_AUTH_SERVICE_TYPE），若环境变量动态变化时 provider 不会自动更新。
- **authProvider 类型未做更细致约束**：部分情况下 authProvider 可能为 null，部分调用未做空值保护。
- **事件监听移除时机不严谨**：useEffect 监听认证事件时，未在 provider 变化时及时移除旧监听，可能导致多余事件绑定。
- **异常处理未区分操作类型**：error 状态未区分登录、登出、token 刷新等不同操作，页面难以精准反馈。
- **Mock/Remote 自动降级兜底不完善**：虽然支持工厂模式，但 provider 创建失败时仅简单 fallback 为 mock，未有详细兜底逻辑。
- **部分副作用未做防抖**：如 updateAuthState、initProvider 等可能被多次触发，建议增加防抖或唯一性保护。
